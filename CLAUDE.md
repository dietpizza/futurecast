# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**DeltaRisk**, called FutureCast until 2026-10-18, when the user had everything renamed: module and command `deltarisk`, home `~/.deltarisk` / `DELTARISK_HOME`, `DELTARISK_API_PORT` / `DELTARISK_WEB_PORT`, localStorage `deltarisk.*` (theme `deltarisk.theme`), console handle `window.deltarisk`. Migrations: `paths.Home` honours a legacy `FUTURECAST_HOME` and moves an old `~/.futurecast` to `~/.deltarisk` the first time the default is needed (only if `~/.deltarisk` doesn't exist; tests point both at temp folders through `paths.DefaultHome` / `paths.LegacyHome`, never the real ones); `live.svelte.ts` copies old `futurecast.*` keys once and `index.html` falls back to the old `fc-theme`. The repository folder and git remote keep the old name. The logo and favicon are one flat SVG (`web/public/favicon.svg`: cyan tile, dark Δ, red square; no strokes or glow).

The backend is Go (rewritten from Python on 2026-10-18/19, plan and history in `GO-REWRITE-PLAN.md`). A local, read-only web dashboard for intraday trading of CoinDCX futures pairs. For each tracked coin and each holding window (5m, 15m, 30m, 1h, 2h, 3h, 4h, 8h) it serves the **long and short risk**: the chance a position opened now hits the user's stop within the window (the 0–100 score), the 1-in-10 bad case, the liquidation chance and the main reason, from a per-coin HAR volatility baseline that passes a walk-forward check. Also per window: **momentum** and **market state** (rules, not forecasts) and **volatility**, and per coin the **funding rate**. The stop is on margin (the PnL % CoinDCX shows, −5% to −10%), so it depends on the coin's leverage tier. `deltarisk risk` prints the models' check and today's readings; `deltarisk backtest` separately replays two rule-based setups (fair-value-gap setups, wedge breakouts) on history; they are not on the dashboard. It doesn't trade: it only calls Binance's public market-data endpoints and has no API keys or order code. The user removed the old `safety.yaml` / zero-execution startup check on 2026-10-17 as pointless for an app with no trading access; don't add it back.

History of models: on 2026-10-17 the user first had every model removed (setup classifiers, trade-risk quantiles, HMM regimes, the residual-alpha ensemble) and ran a momentum event-study dashboard; the same day they asked for predictive risk analysis instead and chose this design (plan and decisions in `docs/risk-plan.md`). LightGBM quantile models ran next to the HAR baseline until the Go rewrite, which dropped them: they shipped in 9 of 96 window-sides, moved scores by about 2 points and improved the Brier score by 0–4%. Don't build a direction classifier: on real BTC/ETH/SOL/BAT/INJ/DASH history the next move's direction was indistinguishable from chance; risk comes from the size of moves, which volatility clustering makes predictable.

Go 1.25 (`go.mod`, module `deltarisk`); the page is Svelte 5 + Tailwind 4 built with Vite in `web/` (npm). Both toolchains come from `mise.toml` (`go`, `node`); run Go through `mise exec -- go …` when `go` isn't on the PATH. No linter is configured beyond `go vet` and `gofmt`. Tasks are in `mise.toml`:

mise run test                                      # go test ./...

go test ./...                                      # full suite (~20 packages, ~15 s, no network)
go test -race ./...                                # the manager, board and server run goroutines: keep this clean
go test ./internal/risk -run Parity -v             # one package, by name

go run ./cmd/deltarisk                             # dashboard on 0.0.0.0:8000 (`deltarisk web` is the same)

Runtime state lives in `~/.deltarisk`, or `$DELTARISK_HOME` if set (`internal/paths`). When running the server to check a change, point `DELTARISK_HOME` at a temp folder so the user's watchlist isn't touched. Tests set `DELTARISK_HOME` and the default/legacy folders to temp ones in every package that reaches the home folder, and never call the network: Binance is faked by `internal/binance/binancetest` (an `httptest` server with a shared fake clock), the catalog by a stub lister.

## Architecture

**Packages.** `cmd/deltarisk` (cobra: the dashboard as the root command and `web`, `risk`, `backtest`) → `internal/server` (`net/http` routes + `/ws` hub on `github.com/coder/websocket`) → `internal/manager` (the hub). Market data: `internal/binance` (client), `internal/cache` (Parquet caches), `internal/pq` (flat Parquet files with key-value metadata, on `arrow-go`), `internal/candles` (`Bars`, `Funding`, `Chart`, `Align`), `internal/catalog` (pair names, sectors, benchmarks, the search list), `internal/history` (chart sizes, the cached client, aligned downloads). Statistics: `internal/series` (pandas and numpy operations), `internal/regime`, `internal/funding`, `internal/risk`, `internal/jsonx` (NaN, missing labels and timestamps in JSON). Backtests: `internal/setups`, `internal/wedges`, `internal/backtest`. `internal/config` reads `<home>/config/assets.yaml` over built-in defaults.

**Data flow.** `manager.Manager` holds one `Worker` per tracked coin (insertion order is the page's order) and `Run` is the stream loop: live prices on every poll (3 s), candles plus rescoring only when a 5m, 15m or 1h candle closes, and a retrain (`ScheduleTraining`) once a coin's models are `RetrainAfter` (24 h) old. Every snapshot goes to browsers as a `FORECAST_UPDATE` WebSocket message (the name is historical); a new socket gets `INIT_STATE` first (queued before it joins the hub), removals send `COIN_REMOVED`. Whatever the page sends on `/ws` is read and dropped. Snapshots and API responses carry only what the page reads (the user had all unused code and fields removed on 2026-10-17); add a field when the page starts using it. Errors are `{"detail": …}` with FastAPI's codes (400 bad symbol or override, 404 untracked coin, 422 malformed body). `PATCH /api/coins/{symbol}` sets a coin's tier and/or leverage override (null resets; fields left out stay). `/api/coindcx/futures` returns the whole catalog and the add-pair drawer (`Sidebar.svelte`) searches and filters it. `GET /api/market` feeds the drawer's market board (`internal/board`): price, 24h quote volume and % change over 5m/15m/1h/4h/24h for every catalog pair. 24h figures come from one all-symbol `/fapi/v1/ticker/24hr` call every 30 s; shorter changes from a per-market price history seeded with the last 245 one-minute closes (`RecentCloses`, weight 2, 3 in flight, only markets the page asked about: ~525 fill in under 2 minutes) and extended at every poll. It starts on the first request (which waits up to 5 s for the first poll), stops after 10 idle minutes, and is empty offline. The drawer polls it every 10 s while open and remembers its change window and sort (`deltarisk.board.*`). INR prices and CoinDCX's max leverage aren't shown: CoinDCX is never called.

**Symbols.** CoinDCX names (`B-SOL_USDT`, `I-BTC_INR`) are the IDs everywhere: API, persistence. All market data (candles, settled funding rates, prices) comes from the Binance USD-M perpetual behind the pair (`binance.Candidates`: `B-SOL_USDT` → `SOLUSDT`, `B-1000PEPE_USDT` → `1000PEPEUSDT`, INR pairs → their USDT perpetual). The add-coin catalog (`catalog.Catalog`) is Binance perpetuals renamed to CoinDCX form plus a curated registry (`catalog/tables.go`, with the sector table). Each coin gets one sector-aware benchmark (`catalog.Benchmark`, e.g. meme coins → DOGE, leaders and unlisted coins → BTC), downloaded and aligned with it; its volatility is a risk input (`market_rv`). A coin is never its own benchmark (BTC → ETH): its candle columns would collide.

**History.** `Worker.DownloadHistory` downloads `history.Bars` closed candles per chart (25,920 5m ≈ 90 days, 17,280 15m ≈ 180 days, 17,520 1h ≈ 2 years) for the coin and its benchmark, the coin's settled funding rate on `history.FundingCharts` (1h), and aligns them (`candles.Align`, columns `{SYMBOL}_close` etc.); `PrepareModels` then trains (`risk.Train`, about a second a coin; there is no model cache any more). `status` goes pending → queued → downloading → training → ready (or failed, with `error`); `progress` (label, step of steps, candles done of total, fraction) feeds the dashboard's progress bar. Downloads and training run on two one-slot channels (`Manager.LoadHistory`): the next coin downloads while the previous one trains, and a downloaded coin waits in "training" with a "waiting to train" progress label. Daily retrains queue on the training channel while the old models keep serving; in live mode coins are queued on add and at stream start, and `POST /api/coins/{symbol}/reload` requeues one. After that `RefreshCandles` appends each closed candle (keeping `history.Bars`), rescores the windows on the charts that changed and rereads funding; it does nothing until the worker is ready. Offline mode (`LoadSynthetic`) fills `OfflineBars` random-walk candles per chart and trains on them, so it is ready at once and tests stay fast. A worker's fields sit behind its mutex; charts are replaced, never changed in place, so training works on a copy of the map.

**Risk models** (`internal/risk`; read its package doc in `inputs.go` before changing anything). Windows are `regime.Windows`: 5m/15m/30m/1h = 1/3/6/12 5m candles, 2h/3h/4h = 8/12/16 15m candles, 8h = 8 1h candles. Per window of h candles and side:
- **Target:** `AdverseMoves`: long (close − lowest low of the next h candles) / close, short (highest high − close) / close, ≥ 0, NaN for the last h rows. Divided by the HAR forecast (`Har`: least squares through QR on gonum of the next h candles' log mean Parkinson volatility on `HARColumns`, log rv/pk over 1, 4, 24, 96 windows), so targets are in "swing units".
- **Inputs** (`Inputs`, all known at the close: `TestInputsNeverUseLaterCandles` pins it): HAR columns, momentum/efficiency/vol_pct from the regime, the last window's move, taker-buy share over 1 and 4 windows, range position over 24 windows, UTC hour and hours to the next 8-hourly funding, funding rate and its 90-day percentile (1h chart, as-of on close times), the benchmark's log rv. Only the HAR columns feed the model now; the rest are kept for the parity tests and a future model.
- **Model** (`Model`): the training rows' empirical distribution of swing-unit moves × today's forecast. Stop-hit / liquidation chance is the empirical share above the move (`Chance`). `ExceedChance` (linear between quantiles, exponential tail) is what the page uses to re-read the sent quantiles for another stop.
- **Check** (`WalkForward`, folds in parallel goroutines): expanding train on the first 60%, 4 test blocks, gap h + 8h of candles (`Spec.Gap`). `checked` = the bad case (q90) exceeded in 7–13% of test windows, else the page shows "—".
- **Serving** (`risk.Coin`): `Train` runs the check and fits every window with ≥ `MinTraining` rows; `Score` forecasts at the latest close of given charts; `View(leverage, mmr, stopPct)` gives per window the regime labels, `swing_pct`, and per side `checked`, `coverage`, `bad_case_pct`, `bad_case_margin_pct`, `stop_hit_chance`, `score` (= round(100 × stop-hit chance); the user chose this over 100 × bad case / stop, which read 100 almost everywhere at 20×), `liquidation_chance`, `reason` (`Reason`), and `quantiles` (dense `PageAlphas`) so the page can re-read the chance for another stop.
- **Tiers** (`CoinTier`, `Tiers`): megacap (BTC, ETH, SOL, BNB, XRP) 20×, shitcoin (sector MEME or < $50M 24h quote volume, from the 1h candles) 3×, else altcoin 10×; fixed maintenance rates 0.4/0.5/1%. The stop is on margin: `StopMove = stop% / leverage` (−5% at 20× = 0.25% price); liquidation ≈ 1/L − mmr. Overrides live on the worker (`SetOverrides`) and in the watchlist file.

Results (Oct 2026, ETH/SOL/DASH/ZK/BTC): the baseline's coverage was 7–13% in 77 of 80 window-sides (ZK shorts 2h–4h failed at 13–15%); stop-hit calibration within ~2 points.

**Momentum and market state** (`internal/regime`, rules, no model). Over L = 3 windows (at least 12 candles): momentum −100..+100 = mean of the L-candle return z and the EMA(L) slope z, / `MomentumScale` 2, clipped; bullish/bearish beyond ±25. Efficiency = |net move| / Σ|moves|. Volatility percentile = std of returns over L ranked over 30 days (calm ≤ 25, high ≥ 75, wild ≥ 90). State: wild (pct ≥ 90) → trending (efficiency ≥ `TrendThreshold`, 0.35 × √(12 / L), and |momentum| ≥ 25) → quiet (pct ≤ 25) → choppy. The √L scaling keeps trending at ~15–26% of candles in every window on ETH; neutral momentum is ~60–75%.

**Trend record** (`regime.ComputeTrendRecord`, computed at training, served as `trend_record` per window): after past trending bullish (bearish) readings, how often the next window closed up (down) and the mean move, against every reading and the 0.177% round trip. On ETH/SOL/DASH/ZK (Oct 2026) it was 41–51%, mostly below the coin's base rate, with mean moves within about ±0.2%: following the trend had no edge, in line with the earlier event study.

**Funding** (`internal/funding`, `View`): the latest settled rate on the 1h chart, its mean and percentile over 90 days; nil without a funding column (offline).

**Setup rules (backtest only).** Not on the dashboard and not trained:
- **Rules** (`internal/setups`: `structure.go`, `setups.go`): swing points (`swingLen` candles each side, so a swing is only known `swingLen` candles later), market structure (a *close* beyond the latest unbroken swing: BOS with the trend, CHoCH against it) and fair value gaps (first candle's wick and third candle's wick don't overlap; a gap stays a zone until a close through its far side or `maxAge` candles). The charts are `Spec.LtfMinutes` (entries) and `HtfMinutes` (context), 15m in 1h by default; every count in `Spec` is in candles of its own chart. `FindSetups` turns every entry-chart CHoCH whose move left a gap into a setup: limit at the gap's midpoint, stop just past the pullback's extreme, take-profits at `Spec.Targets` (2R, 3R, 4R). Two context-chart checks (context trend the trade's way; pullback into a standing context gap) make it grade "A+", else "B".
- **Outcomes** (`setups.Outcomes`, `ResolveTrade`): the limit waits `FillWindow` entry candles and is cancelled if price first runs `CancelR` (3R) away; a filled trade wins on take-profit before stop, the fill candle can only stop it out, both in one candle is a loss, and `MaxHold` candles without either is a timeout at that close. Results are in R; anything the data doesn't cover yet stays open (NaN).
- **Backtest** (`internal/backtest`): the rules alone, replayed like one account: only the chosen grades (A+), one setup at a time, a fixed % of equity risked per trade, compounding, after fees; reports win rate vs break-even, R before and after fees, profit factor, drawdown, streaks, monthly and per side (`FormatReport`, `WriteCSV`). Results on 2 years to Oct 2026 (A+, 3R, per trade after fees): 15m/1h ETH +0.06R, SOL −0.01R, BAT +0.01R, BTC −0.56R; other chart pairs worse. Before fees A+ setups are near 0R almost everywhere.
- **Costs** (`Spec.MakerBps`, `TakerBps`, `SlippageBps`, `RoundTrip`; `setups.BreakEven`): per leg, by how the trade ended. The limit entry and a win's take-profit pay maker, a stop pays taker plus slippage, a timeout taker. Defaults are CoinDCX USDT-M futures with 18% GST (0.0295% / 0.0885%) and 2 bps of stop slippage (assumed). The CLI takes `--maker`, `--taker`, `--slippage` in bps.
- **Wedge breakouts** (`internal/wedges`, `backtest.Wedge`, `--strategy wedge`): one chart. Lines through the latest two swing highs and two swing lows known by the previous candle, converging, apex 10–30 candles past the breakout, no close outside them since the first pivot; a close beyond a line breaks out (A+: volume 1.5× its 20-candle mean and body > ATR(14)), watched by one state machine per chart: a retest within `RetestTolerance` of the line within `RetestWindow` candles, a close that far back inside fails it, and the retest candle or the next must close the trade's way in its top/bottom half. Market entry at that close, stop `StopATR` ATR past the retest, targets 2R, 2.5R and measured, stop to `BreakevenStop` after `BreakevenAt`. `Config.MaxLeverage` (CLI default 5 for wedges) shrinks the risk of too-tight stops. Results, all grades, 2R after fees: 15m −0.2 to −0.5R, 1h −0.04 to −0.4R, 4h over 6 years and 10 coins −0.02R on 212 trades; ~0R before fees everywhere.

**Candle cache.** `cache.Candles` keeps closed candles on disk in `<home>/cache/candles/<BINANCE_SYMBOL>_<interval>.parquet`, keyed by Binance market so pairs and benchmarks share files (the dashboard and the backtest CLI share them; `history.CacheBars` 120k rows). Each file records the span of open times it fully covers (Parquet key-value metadata `covered_from`/`covered_to`; 0 means back to the listing), and the client downloads only what lies outside that span. Settled funding rates are kept the same way in `<home>/cache/funding/<BINANCE_SYMBOL>.parquet` (`cache.Funding`: events from `covered_from`, complete up to `fetched_at`), so a restart fetches only settlements since. The format is the one the Python app wrote with pyarrow (flat `time` int64 + float64 columns, `count` int64, zstd); Go and pyarrow read and append to each other's files. Clients get the caches only when constructed with them (`history.Client` does, from `assets.storage`), so tests with a bare client stay uncached.

**Watchlist.** `<home>/tracked_symbols.json` holds the coins the user added as `{"symbol", "tier", "leverage"}` objects (null = automatic) and is rewritten on every add, remove and override; the older plain-list format still loads. There are no default coins: with nothing saved the watchlist starts empty. `server.Options.InitialSymbols` overrides the saved list, which tests use.

## Gotchas

- **Parity with the Python results:** `internal/testdata/parity/` holds the Python code's answers on fixed ETH/BTC candles (written by `scripts/parity_dump.py`, deleted with the Python code; both are in git history before commit `Go rewrite phase 9`), and the `Parity` tests compare to them, so they are now plain regression tests (labels exactly, numbers to 1e-9, fits to 1e-6). A mismatch means a semantics bug; don't loosen the tolerance. `internal/series` copies pandas 3's own algorithms (Kahan-compensated rolling sums, Welford variance that recomputes ill-conditioned windows, ranks with ties averaged, EWM from the centre of mass, numpy's quantile interpolation); its tests use `series.json`.
- **FMA:** Go may fuse `a*b + c` into one fused multiply-add on arm64, even across statements, which rounds differently from numpy. Where a result must match exactly or feeds a comparison (quantile interpolation, wedge lines, take-profit levels, equity), wrap the product in `float64(...)`. pandas' EWM is itself fused on arm64, so `series.EWMMeanCom` uses `math.FMA` there.
- **NaN rules:** a comparison with NaN is false, so pandas' `.where(x > 0, other)` puts `other` where x is NaN; rolling windows need all `n` values unless a minimum count is given. JSON can't carry NaN: use `jsonx.F` (NaN/Inf → null), `jsonx.Label` ("" → null) and `jsonx.Stamp` (pandas' timestamp text) in anything the page reads.
- **Config:** `config.Load` reads `<home>/config/assets.yaml`, not the repo's `config/` folder. The repo YAML only documents the defaults; the real defaults are `config.Default()`. Unknown keys in home config files are ignored.
- **Window units:** positions count candles, not clock time; gaps the aligner dropped are stepped over. `regime.Spec.CandlesIn` converts days to candles of the window's chart. `setups.Spec` counts `Ltf*`, `FillWindow` and `MaxHold` in entry candles and `Htf*` in context candles.
- **History length vs. the models:** the risk models need thousands of past windows: 90 days of 5m give ~2,160 non-overlapping 1h windows, 2 years of 1h ~2,190 8h windows. The 96-window HAR input needs 96 × h candles of warm-up (32 days for 8h), so shortening `history.Bars` quickly leaves windows untrained.
- **Times:** every time is int64 milliseconds (candles keyed by open time; close = open + step).
- **Alignment drops more than the gap:** like pandas' groupby, a gap longer than 3 candles also drops the candle before it (`candles.Align`).

## Frontend

Svelte 5 (runes) + Tailwind 4 in `web/` at the repository root, built by Vite (no SvelteKit, one page). `internal/server` serves `web/dist` (`--web-dist`, `server.Options.WebDist`): `/` is `index.html` with `Cache-Control: no-cache`, `/assets/*` are Vite's hashed files cached as immutable, and without a build `/` answers 503 with how to make one. In development use `mise dev`; the Vite server proxies `/api` and `/ws` to the backend, so the page code always uses same-origin URLs.

- `src/lib/live.svelte.ts`: the one `$state` object `app` (coins, selected `window`, `stopPct`, open rows `expanded`, connection, catalog, drawer), the REST calls (`updateCoin` for overrides) and the `/ws` stream. The window, stop and sort are saved in `localStorage` (`deltarisk.window`, `deltarisk.stop`, `deltarisk.sort`). Components read it and update on their own; there is no manual re-rendering.
- `src/lib/risk.ts`: `WINDOWS`, `STOPS`, `TIERS`, `reading` (one side's stop-hit chance for the page's stop: the server's exact number at its own stop, else `exceedChance` over the sent quantiles, a port of `risk.ExceedChance` in `internal/risk`; keep them in sync), score bands (`riskTone`: < 25 low, < 50 middle, else high), labels and tooltip texts, loading states. `src/lib/sort.ts`: watchlist sorting (`sortCoins`, `nextSort`): Pair, Call (Long, Short, Wait), Tier (leverage), Long/Short risk (stop-hit chance at the page's stop; unchecked readings sort last), Momentum, Volatility (percentile), Funding (rate); not Price or State. A head click cycles its first direction (text ascending, numbers descending), the other, then off; the sorted head shows a chevron (down = descending). `src/lib/format.ts`: number formatting. `src/lib/types.ts`: the snapshot fields the page reads (`manager.Snapshot`).
- `src/components/`: `Header`, `Toolbar` (title, summary, window selector, stop setting), `Watchlist` → `CoinRow` → `CoinDetails`, `RiskCell` (one side's score, bar and bad case; "—" when unchecked), `Dropdown` (the page's own select: square field, a menu whose current option sits on a soft cyan wash (no notch, no full fill: the user's call); closes on a choice, an outside press, Escape or Tab; arrow keys, Home/End, Enter; the user asked for it instead of native `<select>`, so don't use one), `Sidebar` (add pair), `Glossary` (footer cheat sheet), `Tooltip` (one floating tooltip for every `data-tooltip` / `data-tooltip-title` attribute, through delegated events), `Icon`.

**Styling.** Colors are CSS custom properties in `src/app.css`, defined twice: light in `:root` and dark in `:root[data-theme="dark"]`. Any new color token needs both, plus a `--color-*` line in its `@theme inline` block to get Tailwind utilities (`bg-surface`, `text-muted`, `border-rule`, …); Tailwind's default palette is switched off. Breakpoints are the page's own: `max-lg:` < 1180px, `max-md:` < 980px, `max-sm:` < 720px. Markup uses utilities; shared pieces (`.btn`, `.icon-btn`, `.val-*`, `.risk-*`, `.risk-bar`, `.mom-bar`, `.row-grid`) are in `@layer components` in `app.css`, and things utilities can't say (the open card's HUD brackets, hover gradients, the phone grid areas, the tooltip) are in component `<style>` blocks. Cascade gotchas: utilities beat the components layer, so don't pair a `.val-*` class with a `text-*` utility on one element; unlayered component `<style>` rules beat every utility, so don't set `display` there on something a `max-*:hidden` utility hides. The look is a Cyberpunk 2077 pause menu: square corners, caps labels, red (`--text-muted`) for labels only, cyan (`--accent`) for selection. Numbers and paragraphs that should look quiet use the neutral `--text-dim` (`.val-muted`, `text-dim`), never `--text-muted`, so they don't read as negative. All text is Rajdhani (`--font`, self-hosted in `src/assets/fonts/` with its OFL license). It has no tabular figures, so number columns only roughly align, and text that ticks in place (the header clock) needs a fixed `min-width`. The theme is set before first paint by an inline script in `index.html` and toggled in `Header.svelte`.

**Coin row.** The window selector (`app.window`, default 1h) and the stop (`app.stopPct`, −5…−10% margin) drive every cell.
- **Two kinds of number:** about the next window (long/short risk, swing) and about the last few windows (momentum, state, volatility, funding). Only the column heads are marked: their text is violet `--fwd` (`th-fwd`) or orange `--now` (`th-now`) instead of the label red. The user tried underlines on every value, underlined heads, then a tinted notched background, and settled on plain text color: keep it that way. `u-fwd` / `u-now` color the cheat sheet's terms the same way. The row and the windows table put each kind in its own group of columns, split by a hairline (`.group-start`), with no group labels (the user's choice); the cheat sheet explains the colors.
- **Row** (`CoinRow.svelte`): pair, price (flashes green/red when it moves), the call (Long / Short / Wait, `callOf` in `lib/risk.ts`: trending + bullish/bearish momentum + that side's risk checked and under `CALL_MAX_RISK` 50 at the page's stop; the user asked for it on 2026-10-17 knowing it has no tested edge; its tooltip shows `trend_record`), tier and leverage (`*` when overridden) | long and short risk (`RiskCell`) | momentum (label, value, bar from the middle), state (with efficiency), volatility, funding (crowded at ≥ 90 / ≤ 10 pct). Funding drops out below 1180px, tier, momentum, state and volatility below 980px; phones show pair, call, price and the two risks.
- **Expanded** (`CoinDetails.svelte`): tier select and leverage input (overrides through `PATCH`), the stop as a price move, liquidation distance, funding; every window in a table (long risk, short risk, swing | momentum, state, volatility; clicking a row selects it); then the footer (history span, Reload history / Retry download, CoinDCX link, Remove).

**Checking UI changes.** `--offline` renders everything from random-walk candles (no funding). For real numbers, run the server live with `DELTARISK_HOME` pointed at a temp folder and copy `~/.deltarisk/cache/candles/<COIN>USDT_{5m,15m,1h}.parquet` plus the benchmark's into `<temp home>/cache/candles/` first, so only the newest candles download (without them a coin downloads in about a minute; training takes about a second). `DELTARISK_HOME=<temp> DELTARISK_API_PORT=8765 DELTARISK_WEB_PORT=5199 mise dev` keeps clear of the user's own `mise dev` (5000/5001) and of a dashboard they have running on :8000 (which serves `web/dist` as last built, so it shows source edits only after `mise run build`; its binary is whatever it started with). To try a page build without touching `web/dist`, `npx vite build --outDir <temp>` in `web/` and start the server with `--web-dist <temp>`. View the user's dashboard only: don't add or remove coins there. To preview risk states, run `deltarisk.stopLive()` in the page console (stops the stream so updates don't overwrite your edits), then edit `deltarisk.app.coins[...]`: the page re-renders by itself.
