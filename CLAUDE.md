# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local, read-only web dashboard for CoinDCX futures pairs, built around a fair-value-gap strategy (a higher context chart and a lower entry chart: 1h and 15m by default). For each tracked coin it finds market structure, fair value gaps and setups by exact rules, serves each setup's win chance from LightGBM / XGBoost / CatBoost trained on the coin's own past setups, and a worst-move risk per horizon, plus a secondary cross-asset "residual alpha" forecast. It must never trade: there are no API keys, no order routing, and `AppConfig.enforce_zero_execution_policy()` (`config.py`) refuses to start if `execution_enabled` is true or `air_gapped` is false. Keep it that way.

## Commands

Python 3.12, managed with `uv`. No build step, linter or formatter is configured.

```bash
uv run pytest -q                                   # full suite (~85 tests, ~20s, no network)
uv run pytest tests/test_web.py -q                 # one file
uv run pytest tests/test_web.py::test_web_index_page -q   # one test
uv run pytest -k persistence -q                    # by name

./run.sh                                           # dashboard on 0.0.0.0:8000 (wraps `uv run futurecast`)
uv run futurecast --host 127.0.0.1 --port 8765     # local only, other port
uv run futurecast --offline                        # synthetic random-walk candles, no network, no training

uv run futurecast backtest B-ETH_USDT              # backtest the setup rules: 15m entries, 1h context, 2 years, A+, 3R
uv run futurecast backtest B-ETH_USDT --entry 5m --context 1h --days 365 --target 4 --grade all --csv trades.csv
```

Runtime state lives in `~/.futurecast`, or `$FUTURECAST_HOME` if set (`paths.py`). When running the server to check a change, point `FUTURECAST_HOME` at a temp folder so the user's watchlist and trained models aren't touched. Tests already do this through an autouse fixture in `tests/conftest.py`, which also stubs the Binance catalog so tests stay offline. To check training end to end, build a `SymbolWorker` with `FUTURECAST_HOME` set to a temp folder and call `train_sync()`. It needs network access and takes roughly 4 minutes for a coin the first time (downloading 1m, 15m and 1h candles for the coin and its two benchmarks, then ~50s fitting); later runs read the candles from the cache in a few seconds.

## Architecture

**Data flow.** `cli.py` → `publisher/web_server.py` (FastAPI app, REST + `/ws` WebSocket) → `publisher/multi_manager.py`, which is the hub. `MultiCoinStreamManager` holds one `SymbolWorker` per tracked coin and runs the stream loop: live price and order book on every poll (~3s), and candles, features and model outputs only when a candle closes (every minute for 1m candles). Every snapshot is pushed to browsers as a `FORECAST_UPDATE` WebSocket message.

**Symbols.** CoinDCX names (`B-SOL_USDT`, `I-BTC_INR`) are the IDs everywhere: API, persistence, model file names (via `sanitize_symbol_for_filename`). All market data (candles, settled funding rates, prices, order books) actually comes from the Binance USD-M perpetual behind the pair (`ingestion/binance.py`: `B-SOL_USDT` → `SOLUSDT`, `B-1000PEPE_USDT` → `1000PEPEUSDT`, INR pairs → their USDT perpetual). CoinDCX is never called; the add-coin catalog (`ingestion/coindcx_catalog.py`) is Binance perpetuals renamed to CoinDCX form plus a curated registry. Each coin gets sector-aware benchmarks (`ingestion/factory.py`: `get_symbol_sector`, `resolve_benchmarks`, e.g. meme coins → `[DOGE, BTC]`) that are aligned with it before feature generation. A coin is never its own benchmark (BTC → `[ETH, SOL]`, ETH → `[BTC, SOL]`). Listing it would duplicate its candle columns, and feature generation fails with `'arg1' columns are not unique`. Feature names containing `btc` (`beta_btc_*`, `funding_rate_spread_btc`, …) refer to the primary benchmark, not literally BTC, and `doge` (`doge_btc_ret_spread_15m`, `rsi_spread_doge_btc_14m`) means the target coin. Renaming them changes the models' input columns.

**Setups (primary output).** Rules first, models second:
- **Rules** (`features/structure.py`, `features/setups.py`): swing points (`swing_len` candles each side, so a swing is only known `swing_len` candles later), market structure (a *close* beyond the latest unbroken swing: BOS with the trend, CHoCH against it) and fair value gaps (first candle's wick and third candle's wick don't overlap; a gap stays a zone until a close through its far side or `max_age` candles). The charts are `SetupSpec.ltf_minutes` (entries) and `htf_minutes` (context), 15m in 1h by default (`multi_manager.SETUP_SPEC`, the CLI's default too); every count in `SetupSpec` is in candles of its own chart, so the same rules scale with the charts. `find_setups` turns every entry-chart CHoCH whose move left a gap into a setup: limit at the gap's midpoint, stop just past the pullback's extreme, take-profits at `SetupSpec.targets` (2R, 3R, 4R). Two context-chart checks are recorded, not required: the context trend points the trade's way, and the pullback reached into a context-chart gap that existed before price got there and still stands. Passing both makes it grade "A+", else "B"; only A+ setups raise a signal, but B setups stay in training. `setup_features` makes everything side-relative (a mirrored short gives the same features as the long, `test_shorts_mirror_longs_exactly`).
- **Outcomes** (`labels/setups.py`): the limit waits `fill_window` entry candles and is cancelled if price first runs `cancel_r` (3R) away, the same level for every target so a setup's fill doesn't depend on the target; a filled trade wins on take-profit before stop, the fill candle can only stop it out, both in one candle is a loss, and `max_hold` candles without either is a timeout at that close. Results are in R; anything the data doesn't cover yet stays open (NaN).
- **Models** (`models/setup_model.py`): `SetupModel` trains one classifier set per target on filled, resolved setups (setup features joined with the entry chart's market features at the setup candle). Purged time slices drop rows whose trade resolves after the next slice starts. The baseline is the rules alone: the win rate of the setup's grade. Edge needs a bootstrap lower bound on Brier skill against it above 0 and a better AUC than the grade; otherwise the grade's win rate is served (`probability_source: "rules"`). Replays of the test stretch, one setup at a time after fees: every A+ setup (`rules_replay`) and A+ setups whose chance clears break-even (`model_replay`). `TargetModel.validated` means the replay behind the served chance made money on ≥ `min_signal_trades` (10) trades. The module docstring has the details; read it before changing anything there. On real BTC/BAT/SOL history the models found no edge over the rules (AUC ≈ 0.5).
- **Backtest** (`backtest.py`, `futurecast backtest`): the rules alone, replayed like one account: only the chosen grades (A+), one setup at a time (a waiting order or open trade blocks the next), a fixed % of equity risked per trade, compounding, after fees; reports win rate vs break-even, R before and after fees, profit factor, drawdown, streaks, monthly and per side. Training stores one per target on the training history in `SetupModel.backtests` (`dashboard_view`: no trade list) for the dashboard's Backtest block. Results on 2 years to Oct 2026 (A+, 3R, per trade after fees): 15m/1h with per-leg fees ETH +0.06R, SOL −0.01R, BAT +0.01R, BTC −0.56R (a flat 0.10% gave +0.08, +0.02, +0.02, −0.50); with a flat 0.10%, 15m/4h negative on all four, 5m/1h −0.1 to −0.5R and 1m/15m −0.4 to −0.9R, where fees are 0.4–0.7R of a 0.15–0.25% stop. Before fees A+ setups are near 0R almost everywhere.
- **Costs** (`SetupSpec.maker_bps`, `taker_bps`, `slippage_bps`, `round_trip`; `labels.setups.trade_cost_r`, `break_even`, `expected_r`): per leg, by how the trade ended. The limit entry and a win's take-profit pay maker, a stop pays taker plus slippage, a timeout taker. Defaults are CoinDCX USDT-M futures with 18% GST (0.0295% / 0.0885%) and 2 bps of stop slippage (assumed). Break-even and expected results charge every non-win the stop's cost; backtests and replays charge each trade its own. The CLI takes `--maker`, `--taker`, `--slippage` in bps.
- **Live** (`engine/setups.py`): `live_view` runs the rules on the live entry and context buffers (no model needed, so untrained coins show structure and setups, with null chances), takes the latest setup per side, its order state on the candles since, and a trained model's scores. `signal` is LONG/SHORT only for a waiting A+ setup whose chance clears break-even and whose target is validated. `setup_dataset` builds the same table for training.

**Trade risk:** `models/trade_risk.py`. `TradeRiskModel` is trained per candle interval: `HORIZONS_BY_INTERVAL` maps 1m candles → 5m/15m/1h horizons and 15m candles → 4h/8h, with purged slices one horizon apart. Quantile regressors learn the 95th percentile of the adverse excursion (worst move against each side, `labels.barriers.adverse_excursion`), measured in volatility units, with a conformal calibration step that is done per volatility regime (`models/regimes.py`: a 3-state Gaussian hidden Markov model of log returns, calm/normal/stormy, fitted on the oldest 40% of history and only ever filtered forward), so the 95% holds in stormy stretches, not just on average. `coverage_by_regime` reports test coverage per regime next to what a `single_scale` would give; regimes with fewer than `min_regime_windows` independent windows fall back to the single multiplier. The payload carries `regime`, `regime_probs` and `storm_chance`. The model is served only if it beats a volatility-only baseline on the test slice; otherwise the baseline is served. It outputs a worst-move %, a 0–100 score ranking it against the coin's recent history, and a max leverage. There is no rule-based risk score: untrained coins show none.

**Residual alpha (secondary):** `models/ensemble.py` (`MultiModelEnsemble` regressors) driven by `engine/forecaster.py` (`PureForecastEngine`) on 1m candles with a 15-minute horizon. It writes JSONL forecast logs through `publisher/broadcaster.py`, at most `forecasting.log_limit_mb` (32 MB) in total: files roll over at a quarter of the limit and the oldest are deleted first. Every coin's engine has its own broadcaster on the same folder, so writes are serialised per folder. The dashboard doesn't show residual alpha, but it still trains and logs.

**Training.** `SymbolWorker.train_sync` fetches up to `HISTORY_BARS` real candles per interval (100k 1m ≈ 69 days, 70k 15m and 17.5k 1h ≈ 2 years) for every chart in `CANDLE_MINUTES` (the risk intervals plus the setup charts) and needs at least `MIN_TRAIN_BARS`. It downloads every interval first (`training_status` "downloading"), then fits (`"training"`: risk models per `RISK_INTERVALS`, then setups from the entry and context histories, the `SetupModel` and its backtests, then residual alpha), and keeps `training_progress` (stage, label, step of steps, candles done of total, overall fraction) current for the dashboard. It never trains on synthetic data. It runs in a thread executor behind one asyncio lock (one coin at a time), saves models to `<home>/models/` (`setup_model_<sym>.joblib`, `trade_risk_<sym>_<interval>.joblib`, `lightgbm_<sym>_residual_alpha.txt`, …), and hot-swaps them under the worker's lock. A coin counts as trained only when its setup model (trained on `SETUP_SPEC`'s charts; one for other charts is dropped) and both risk models load. The live loop reruns setups only when an entry or context candle closes. In live mode untrained coins are queued automatically when streaming starts. A model whose `FORMAT_VERSION` doesn't match is ignored, so bumping the version forces a retrain.

**Candle cache.** `ingestion/cache.py` `CandleCache` keeps closed candles on disk in `<home>/cache/candles/<BINANCE_SYMBOL>_<interval>.parquet`, keyed by Binance market so pairs and benchmarks share files. Each file records the span of open times it fully covers (Parquet metadata `covered_from`/`covered_to`; 0 means back to the listing), and `BinancePublicClient._closed_klines` downloads only what lies outside that span: newer candles, then older ones. Clients get a cache only when constructed with one (`multi_manager._binance_client` does, from `assets.storage`), so tests with a bare client stay uncached. Funding rates are not cached on disk (one request per symbol).

**Watchlist.** `<home>/tracked_symbols.json` holds the coins the user added and is rewritten on every add/remove. There are no default coins: with nothing saved the watchlist starts empty. `create_app(initial_symbols=...)` overrides the saved list, which tests use.

## Gotchas

- **Config:** `load_config()` reads `<home>/config/*.yaml`, not the repo's `config/` folder. The repo YAML files only document the defaults; the real defaults are the pydantic models in `config.py`. Editing `config/*.yaml` in the repo changes nothing at runtime.
- **Window units:** feature window settings named `*_min` (e.g. `beta_windows_min: [60, 1440]`) are passed straight to `rolling(n)`, so they count candles, not minutes. On 1m candles that matches their names (1440 is 1 day); on 15m candles 1440 is 15 days. The exception is `funding_ema_window_min`: it is a clock-time window in minutes (a 3-day trailing mean). `LIVE_BARS` (6,000) must stay above both the longest candle window and, at 1m, the 4,320 candles of that 3-day mean, or live features drift from the trained ones (`test_funding_features_match_between_training_history_and_live_buffer` catches this). `BarrierSpec.vol_window` (240) also counts candles: 4 hours of 1m candles, 60 hours of 15m candles. `SetupSpec` counts `ltf_*`, `fill_window` and `max_hold` in entry candles and `htf_*` in context candles.
- **Timestamps:** under pandas 3 a candle index may be stored in microseconds, so `.asi8` is not nanoseconds. Compare candle times across frames with `features.setups.close_times` (it converts to ns), not raw `asi8`.

## Frontend

Plain HTML/CSS/JS in `publisher/web/`, with no bundler or framework. `index.html` loads `static/js/*.js` in order as classic scripts that share globals; the markup calls them from inline `onclick` handlers. Static files are served with `Cache-Control: no-cache` (`RevalidatingStaticFiles`), so edits show on reload without restarting the server. Colors are CSS custom properties defined twice in `static/css/main.css`: light in `:root` and dark in `:root[data-theme="dark"]`. Any new color token needs both. The look is a Cyberpunk 2077 pause menu: square corners, mono caps labels, red (`--text-muted`) for labels only, cyan (`--accent`) for selection. Numbers and paragraphs that should look quiet use the neutral `--text-dim`, never `--text-muted`, so they don't read as negative. All text is Rajdhani (`--font`, self-hosted in `static/fonts/` with its OFL license). It has no tabular figures, so number columns only roughly align, and text that ticks in place (the header clock) needs a fixed `min-width`. The theme is set before first paint by an inline script in `<head>` and toggled by `theme.js`.

**Coin card.** `app.js` re-renders each card with `innerHTML` on every `FORECAST_UPDATE` (~3s), so UI state that must survive a refresh lives in window-level maps (`expandedCards`).
- **Row:** signal pill, the latest long and short setup (`setupCell`: win chance and break-even while the order waits, else grade and what happened), the context / entry trend (`trendCell`), order book, and risk for the selected horizon. The horizon selector only drives risk.
- **Layout:** the expanded card holds only what decides a trade (the user asked for exactly that after a cluttered version; don't add model test stats, calibration, risk or order-book blocks back). `tradeBlock` shows a panel per *live* A+ setup (`liveSides`: limit waiting, or filled and running) with the verdict pill and five numbers at full contrast (entry, stop, target, win chance, size); with none live it says "No trade" and what the next setup needs (`waitingFor`: context trend and its nearest gap), plus one quiet line on the other setups. Then `backtestBlock` (one row per target: trades, won vs needed, average R, account, drawdown, equity sparkline, a Made money / Break-even / Lost money tag) and `levelsBlock` (`.detail-quiet`: each chart's trend and last break, the context chart's nearest gaps). Win chance turns green only when it clears break-even; no-trade states are said by the pill and panel color, never by dimming numbers.
- **Verdicts:** `setupVerdict` re-derives each side's verdict from the server fields and mirrors the signal rule in `engine/setups.py`; the record it quotes is the served target's `model_replay` when the models have an edge, else `rules_replay` (from `coin.setup_model`). `MIN_SIGNAL_TRADES` hard-codes the 10-trade replay minimum (`min_signal_trades`), so change them together.
- **Order book:** display-only; no model uses it.

**Checking UI changes.** `--offline` renders structure and setups from synthetic candles but has no trained models, so win chances and the Backtest block stay empty unless the home folder already holds a `setup_model_<sym>.joblib`. To see them, train a coin into a temp home: copy `~/.futurecast/cache/candles/*.parquet` (1m, 15m and 1h) for the coin and its benchmarks into `<temp home>/cache/candles/` and call `SymbolWorker.train_sync()` (then only the newest candles are downloaded), or fit a `SetupModel` on `engine.setups.setup_dataset` over `_synthetic_candles` as `test_web.py` does. If the user's dashboard is running on :8000, it serves the working tree's static files, so a reload shows edits, but its Python is whatever it started with: after a payload change the new page needs a restarted server. View it only: don't train, add or remove coins there. To preview signal states, first close the socket in the page (`ws.onclose = null; ws.onmessage = null; ws.close()`), then edit `coinsData` and call `renderCoinCard`. Otherwise the next update (or the reconnect) overwrites your edits within seconds.
